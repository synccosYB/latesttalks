Replace Stripe Membership Checkout with Sola Payments
What and why

Replace the current Stripe checkout on the Latest Talks+ membership page with a complete Sola Payments integration.

The page already has:

Monthly membership: $9.99/month
Annual membership: $120.00/year
“Choose Monthly” and “Choose Annual” buttons
Stripe payment logos and “Secure payment powered by Stripe”

The design should remain substantially the same. This task is about replacing the payment infrastructure and making membership activation reliable, secure, and fully synchronized with Sola.

Use Sola iFields + the Sola Customer and Recurring API, not raw card inputs and not a fake payment form. Sola recommends iFields for custom checkout pages because card and CVV data are tokenized without touching our server.

When a visitor clicks Choose Monthly or Choose Annual, open a professional checkout modal or dedicated checkout section on the same site.

Do not collect card number or CVV through normal application inputs. Those fields must be hosted through Sola iFields and exchanged for Sola single-use tokens before the backend processes the payment.

Backend endpoints

Build the following endpoints.

POST /api/payments/sola/start-membership

Authenticated user required.

Request:

{
  "planCode": "latest_plus_monthly",
  "cardToken": "single-use-token",
  "cvvToken": "single-use-token",
  "expiration": "MMYY",
  "billingZip": "10950",
  "name": "Customer Name",
  "email": "customer@example.com"
}

Backend responsibilities:

Validate the selected plan against the server-side database.
Never trust an amount sent by the browser.
Refuse inactive or unknown plans.
Prevent duplicate active subscriptions.
Create or retrieve the Sola customer.
Create the reusable Sola payment method from the approved tokenized payment flow.
Process the initial payment.
Create the monthly or annual recurring schedule using the Sola Customer and Recurring API.
Save all Sola IDs and transaction references.
Activate the membership only after confirmed approval.
Return a safe response without sensitive gateway data.

Sola’s recurring API supports customers, payment methods and recurring schedules. Authentication must use the API key in the server-side authorization header.

Use a unique invoice number for every attempt, for example:

LT-MEM-{userId}-{timestamp}

Sola recommends sending a unique invoice identifier to help detect accidental duplicate transactions.

POST /api/payments/sola/cancel-membership

Authenticated user required.

Behavior:

Default to canceling at the end of the current paid billing period.
Update the corresponding Sola recurring schedule.
Set cancel_at_period_end = true.
Do not immediately remove paid access unless explicitly requested by an administrator.
Return the final access expiration date.
POST /api/payments/sola/change-plan

Authenticated user required.

Support:

Monthly to annual
Annual to monthly

For the initial release, schedule the new plan to begin after the existing paid period rather than calculating complicated mid-cycle prorations.

GET /api/membership/status

Return:

{
  "isPremium": true,
  "status": "active",
  "plan": "latest_plus_monthly",
  "currentPeriodEnd": "2026-08-20T00:00:00Z",
  "cancelAtPeriodEnd": false
}
POST /api/payments/sola/webhook

This must:

Accept Sola’s form-encoded webhook POST.
Preserve the raw request body required for signature validation.
Read the ck-signature header.
Validate it using the configured Sola webhook PIN.
Reject invalid signatures.
Log the event safely.
Deduplicate previously processed events.
Match the event using Sola reference number, invoice number, customer ID or schedule ID.
Update payment and membership status.
Return a quick successful response and process safely without timing out.

Sola webhooks are POSTed as key-value form data. When a webhook PIN is configured, Sola sends a ck-signature header that must be validated.

Handle at minimum:

Approved initial payment
Approved recurring payment
Declined recurring payment
Error
Void
Refund
Chargeback
ACH return, only if ACH is enabled later

A browser redirect or frontend success response is not authoritative. The webhook and verified server response must be the source of truth.

Payment result handling

Treat Sola results carefully:

Approved: activate or extend membership.
Declined: do not activate; show the safe gateway error.
Error: do not activate; allow retry.
Partial or mismatched authorization amount: do not activate and flag for review.
Duplicate submission: reconcile against the existing transaction instead of creating another membership.

Verify that the amount actually authorized equals the plan amount. Sola responses provide the result, authorized amount and a unique reference number that should be retained for reconciliation and support.

Security requirements
Never let the backend receive raw card number or CVV.
Never log raw webhook secrets or payment credentials.
Redact payment payloads before storing or sending to Sentry.
Apply rate limiting to payment endpoints.
Require authentication and CSRF protection where applicable.
Use server-calculated amounts.
Use database transactions when activating memberships.
Add idempotency around every payment submission.
Validate webhook signatures before changing any records.
Do not unlock premium content from query-string success parameters.
Do not accept a frontend claim that payment succeeded.
Keep sandbox and production keys strictly separated.
